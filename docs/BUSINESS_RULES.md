# BUSINESS RULES: ra-labs

Business rules enforced by the system. Each rule is independently testable.

| ID | Rule | Layer | Test |
|---|---|---|---|
| BR-001 | RAG retrieval for customer content is filtered by `customer_project_id` at the query layer — a project agent **must never** retrieve another customer's chunks. This is a hard filter in the Qdrant query payload, not a prompt instruction or post-retrieval check. | Infrastructure / Qdrant query layer | Create two test customers (A and B), each with one `CustomerProject` and ingested documents producing `KnowledgeChunk` rows with their respective `customer_project_id`. Issue a retrieval query for customer A's project agent. Assert that zero chunks belonging to customer B appear in the result set. |
| BR-002 | Transactional facts — quote figures, timelines, contractual language — are sourced from structured fields (`ClientPrd` or `Invoice`) or trigger `needs_manual_intervention`. The agent may use retrieval to suggest a value during drafting, but **it cannot present a retrieved fact as confirmed** unless a structured field backs it. | Application / AI agent layer | Seed a `KnowledgeChunk` containing a plausible but unconfirmed quote value ($15,000) for a project that has no corresponding `ClientPrd` or `Invoice` record. Ask the project agent for a price quote. Assert that the response sets `needs_manual_intervention = true` (or the equivalent flag) and does **not** present $15,000 as a confirmed quote. |
| BR-003 | Invoicing is cash-only at launch. Every invoice is tracked with status `unpaid` or `paid_cash`. No online payment path exists — any attempt to record a non-cash payment (e.g., card, bank transfer) through the API must be rejected at the application layer. | Application / Domain (Invoice service) | POST to the invoice creation endpoint with a payment method other than cash (or attempt to transition status to a value not in `{unpaid, paid_cash}`). Assert HTTP 400 or equivalent rejection. Verify all existing invoices in the test database have status in `{unpaid, paid_cash}`. |
| BR-004 | `CustomerProject` status transitions are gated: (a) transitioning to `prd_signed` requires **both** `signed_at_customer` and `signed_at_admin` to be non-null; (b) transitioning to `closed` requires a `Feedback` record to exist for the project. | Application / Domain (CustomerProject state machine) | (a) Create a `CustomerProject` in `prd_draft`, set only `signed_at_customer` on the `ClientPrd`, and attempt to transition to `prd_signed`. Assert the transition is rejected. Then set `signed_at_admin` and retry — assert the transition succeeds. (b) Create a `CustomerProject` in `delivered` with no `Feedback` row, attempt to transition to `closed`. Assert rejection. Add a `Feedback` row with a rating and retry — assert success. |
| BR-005 | A public `Project` entry is auto-created only when a `CustomerProject` reaches `delivered` status **and** the associated `Feedback` record has `is_published = true`. The reverse also holds: if feedback is not yet approved, no `Project` entry appears. | Application (project publication service, triggered on status change or feedback approval) | (a) Transition a `CustomerProject` to `delivered` without setting `is_published = true` on `Feedback`. Assert that no new `Project` row exists in the database. (b) Update `Feedback.is_published = true` (simulating admin approval). Assert that a corresponding `Project` row is now present with `is_published = true` and title/summary derived from the `CustomerProject`. |
| BR-006 | Every `AgentTask` execution must produce a logged row (auditability). Agent actions are never silent — at minimum, the row captures `type`, `status`, `payload`, `created_at`, and any terminal status (`completed` or `failed`) with a timestamp. | Infrastructure / AgentTask logging service | Trigger a known agent task (e.g., the GitHub sync agent). After execution, query the `AgentTask` table. Assert that exactly one new row exists for the triggered task, with `type` matching the task invoked, `status` in `{completed, failed}`, `payload` containing the invocation parameters, and `created_at` within the expected time window. |
